## 4. 🧠 架构师新知

今天接触并实操了以下嵌入式开发的核心软硬件概念：

- **NVS (非易失性存储)**：ESP32 的 Wi-Fi 底层强依赖 NVS。代码中如果不先调用 `nvs_flash_init()` 进行初始化，芯片会发生内核恐慌（Panic）并无限重启。
    
- **事件循环 (Event Loop) 与非阻塞**：嵌入式 UI 系统（如 LVGL）绝对不能被网络请求或循环等待卡住。必须使用回调函数或独立的 FreeRTOS 任务（Task）来处理耗时操作。
    
- **算力转移与降维打击 (.jpg vs .bin)**：让 16MB 的单片机去跑复杂的离散余弦变换（解压 JPG）是不合理的。最高效的架构是由算力富余的上位机（PC）将图片解析为 `.bin`（裸内存数据），单片机只需执行极低耗时的内存拷贝（Memcpy）即可刷屏。
    
- **LVGL 内存交接 (Pointer Lifecycle)**：在通过 HTTP 下载完 `.bin` 数据并交给 LVGL 渲染后，绝对不能释放（`free`）这块内存。因为 LVGL 渲染时直接读取的是该内存的物理地址（指针），一旦释放会引发野指针崩溃。
    
- **局域网连通性认知**：右下角显示“无 Internet 连接”不代表局域网瘫痪。只要分配到了同一网段的 IP，设备间依然可以顺畅进行 TCP/HTTP 通信。

- **坑 1：LaTeX 公式超长被“腰斩”截断**
    
    - **真相**：浏览器把长公式视作不可分割的图形，超出了 400px 屏幕宽度。
        
    - **避坑解法（Shift-Left 向左移思想）**：没有选择在 Python 里写复杂的动态缩放代码给烂数据擦屁股，而是直接**从源头定规矩**。给生成笔记的 AI 下达了强制换行规范，要求复杂推导必须使用 `\begin{aligned}` 环境。
        
- **坑 2：ESP32 内存大爆炸（Out of memory）**
    
    - **真相**：贪心下载了一张高达 5.9MB (高度一万多像素) 的 `.bin`。虽然单片机有 8MB PSRAM，但底层 C 语言的 `malloc` 机制受限于内存碎片，单次能申请的最大**连续**内存块死死卡在约 4MB。
        
    - **避坑解法**：临时换用单道题（小体积）进行降维测试通关。这也印证了未来必须上 **SD 卡**进行“边读边画（流式读取）”的架构正确性。
        
- **坑 3：屏幕出现斜向黑线（LVGL 解析罢工）**
    
    - **真相**：跨语言的“内存对齐”惨案。Python 拼凑的 12 字节头部，到了 C 语言编译器（有大小端和位域机制）眼里变成了乱码，LVGL 认不出图片宽度直接报错。
        
    - **避坑解法**：**“生吃”裸数据**！直接抛弃跨语言解析，在 C 语言里强行硬编码 `img_dsc` 结构体，宽度锁死 400，高度用 `数据总大小 / 400` 动态算出，然后直接用指针把纯像素数据塞给屏幕。
        
- **坑 4：左侧文字被“狗啃”与单换行失效**
    
    - **真相**：Pillow 库使用了居中裁剪切掉了左边；Markdown 标准库不认识 Obsidian 的单回车换行。
        
    - **避坑解法**：Python 里引入 `'nl2br'` 扩展处理换行；强制 Pillow 裁剪坐标从左上角 `(0,0)` 开始。

- **坑 1：图片“凭空消失”之谜**

    - **真相（Strapping Pins）**：ESP32 的 `GPIO0` 是特殊的系统配置引脚（用于启动模式切换）。微雪板子在该引脚上有强力的硬件电路干预，导致机械编码器那点微弱的电流拉不动它，信号始终死在“1”的状态。
        
    - **避坑方案**：弃用特殊引脚，迁移到最纯粹的“干净引脚” `GPIO3` 和 `GPIO17`，信号瞬间起死回生。

## 3. 🕳️ 踩坑复盘与物理底层

- **踩坑 1：图标在屏幕上离奇“隐形”**
    
    - **底层真相**：在 LVGL v9 的 `I1` (1-bit 索引) 格式中，单片机只认识 0 和 1，它需要一个“字典”来解释这两个数字代表什么颜色。我们最初的 Python 脚本漏写了这本“字典”。引擎错误地把图标第一行数据当成了颜色定义，导致画出来的全是透明色。
        
    - **架构解法**：在 512 字节的像素数组开头，强制注入 **8 字节的调色板 (Palette)**（索引 0 为纯白 `0xFFFFFFFF`，索引 1 为纯黑 `0xFF000000`）。
        
- **踩坑 2：选中图标调用缩放 API 后变成黑洞消失**
    
    - **底层真相**：1-bit 的黑白屏幕无法显示灰色。当调用引擎的 `lv_image_set_scale` 放大 1.5 倍时，引擎无法在非 0 即 1 的像素间进行数学平滑插值，为了防止内存越界或计算崩溃，底层直接丢弃了绘制任务（Drop draw task）。
        
    - **架构解法（空间换时间）**：单片机算不了的，让电脑算。通过 Python 脚本采用最邻近插值法（Nearest Neighbor）预先生成一套 96x96 的“大号” C 数组。单片机仅在选中时进行物理内存指针的切换。
        
- **踩坑 3：字库编译报错与乱码风险**
    
    - **底层真相**：`.ttc` 字体集合包无法被解析器直接读取；同时，全量中文字库动辄几 MB，远超单片机的 16MB 极限资源。
        
    - **架构解法**：降级使用底层的黑体 `.ttf` (`simhei.ttf`)，并采用**按字裁剪**策略，提取 UI 精确需要的 30 多个字符打包，将内存消耗从 MB 级压缩到 KB 级。

## 3. 🕳️ 踩坑复盘与物理底层 (Pitfalls & Physical Layer)



**坑点 1：电池测出 1.82V（硬件欺骗与涓流抢救）**

* **现象**：一直测出 `1.82V`，拔掉 USB 瞬间黑屏关机。

* **物理真相**：电池严重深度亏电 / 板载 `ON/OFF` 开关未打开导致物理断路。此时 ADC 测到的是充电管理 IC（BMS）由于空载而漏出的**“探测虚电压”**，或处于防止电池爆炸的**“涓流充电（Trickle Charge）”**状态。单片机代码无权干涉纯物理的充电过程。



**坑点 2：SHTC3 I2C 通信失败（`ESP_ERR_INVALID_RESPONSE`）**

* **现象**：读不到数据，防呆机制返回 `-999.0f`。

* **硬件参数**：SDA = GPIO 13，SCL = GPIO 14，设备地址 `0x70`。

* **修复动作**：强制开启 I2C 内部上拉电阻（`enable_internal_pullup = true`），并在唤醒指令（`0x3517`）后强加 `2ms` 延时（`vTaskDelay`），让传感器就绪后再发测量命令。



**坑点 3：UI 渲染乱码/方块（LVGL `%f` 浮点陷阱与自发热）**

* **现象**：串口读到 `26.6C`，但受 ESP32 芯片发热影响偏高；UI 无法显示数据。

* **架构解法（重点）**：

    1.  **物理补偿**：引入 `-3.0` 经验 Offset 值抵消板载自发热。

    2.  **定点数模拟法**：因嵌入式 C 运行库裁剪了针对 float 的支持（避免 FPU 性能消耗），`lv_label_set_text_fmt` 无法处理 `%f`。将浮点数拆解为：`整数部分 + (小数部分*10)`，用 `%d.%d` 的纯整数格式化完美绕过底层 Bug。

    3.  **防缺失降维**：将不稳定的特殊符号 `°` 降级为 ASCII 标准字符 `C`。



**坑点 4：PCF85063 持续报错 Oscillator Stop (OS)**

* **现象**：串口狂刷 OS flag is set，时间不动。

* **原因**：RTC 曾彻底掉电，晶振停止标志位被置 1，芯片自锁以防输出错误时间。

* **修复**：在 NTP 对时后，通过 `pcf85063_set_time` 写入当前时间，并**强制清除寄存器 bit 7**，打通阻塞。



**坑点 5：异步任务的“自杀式竞争”（Wi-Fi 生命周期）**

* **现象**：加入 NTP 闭环后，测试用例 `test.bin` 下载中断。

* **原因**：NTP 任务（`ntp_sync`）极快，执行完后直接触发 `wifi_manager_stop()`，强行掐断了同为异步运行的下载进程。

* **修复**：修改服务器优先级顺序加速国内对时（`ntp.aliyun.com` -> `cn.pool.ntp.org`）；剥离 NTP 任务关闭 Wi-Fi 的权限，确立了**“谁申请，统一释放”**的全局网络生命周期原则。

## 3. 🕳️ 踩坑复盘与物理底层



今天在软硬件结合部踩过的每一个坑，都是嵌入式架构的核心知识点：



* **坑 1：NTP 对完时是 12:40（少了 8 小时）**

    * **物理真相**：NTP 授时服务下发的是 UTC 时间（格林威治时间）。

    * **架构解法**：在调用 `localtime_r` 之前必须显式声明 `setenv("TZ", "CST-8", 1)` 环境变量，否则单片机无法感知地理位置。

* **坑 2：31 字节广播包红字报错（`failed: 4`）**

    * **物理真相**：BLE 协议规定单个广播包（ADV）上限 31 字节。原代码试图同时塞入 128-bit UUID 和 14 位设备名，导致溢出。

    * **工程解法**：采用**“双包策略”**。主广播包（ADV）只放 UUID，设备名（FocusCore_BLE）移入“扫描响应包（Scan Response）”，由手机主动索取时才下发。

* **坑 3：CMakeLists.txt 找不到 `nimble` 组件**

    * **物理真相**：ESP-IDF v6.0 的组件化极度严格。NimBLE 属于蓝牙子模块，但在 `REQUIRES` 里必须写父组件 **`bt`**。

    * **工程解法**：在 `main/CMakeLists.txt` 中配置 `REQUIRES bt nvs_flash esp_driver_i2c`，并同步开启 I2C 驱动依赖，解决 `shtc3.h` 找不到库的问题。

* **坑 4：Web Bluetooth 网页“连不上”蓝牙**

    * **物理真相**：浏览器出于安全考虑，禁止 `file:///` 协议（本地直接打开 HTML）调用蓝牙硬件。

    * **工程解法**：必须通过 `localhost` 本地服务器承载页面，确保在受信任的环境下唤醒配对窗口。
