## 一、整体架构

### 你的系统由三层组成

```
┌───────────────────────────────────────────┐
│  第 1 层：你（提需求、做决策、审批计划）     │
└─────────────────────┬─────────────────────┘
                      ▼
┌───────────────────────────────────────────┐
│  第 2 层：全局规则（GEMINI.md）              │
│  ─ 这是 AI 的"行为准则"                    │
│  ─ 每次对话 AI 都会自动读取                 │
│  ─ 里面写了：必须追问确认、必须带建议选项    │
│  ─ 里面还写了：开局要加载哪 6 个技能         │
└─────────────────────┬─────────────────────┘
                      ▼
┌───────────────────────────────────────────┐
│  第 3 层：6 个核心技能（开局自动加载）        │
│                                             │
│  🧠 brainstorming ──── 帮你想清楚要做什么    │
│  📋 planning-with-files ── 管理计划和进度    │
│  🐛 systematic-debugging ── 修 Bug 不瞎猜   │
│  🧪 test-driven-development ── 先写测试再写代码 │
│  ✅ verification-before-completion ── 防止假完成 │
│  🔧 workflow-by-cixia ── 你的个人调度中枢    │
└───────────────────────────────────────────┘
```

### 原理：为什么要搞这么多层？

**你可能会问**：直接让 AI 写代码不就好了，搞这么复杂干什么？

答案是：**AI 不笨，但 AI 很容易"自作主张"**。

没有规则约束的 AI 会：
- 你说"加个搜索功能"→ 它理解偏了直接写 300 行代码 → 全写错 → 浪费几万 token
- 改完代码说"已完成" → 实际没跑测试 → 上线后才发现 Bug
- 新窗口打开 → 不知道项目什么情况 → 重新读所有代码 → 又花几万 token

加了规则后的 AI 会：
- 你说"加个搜索功能"→ 先问你"搜什么范围？放在哪？" → 对齐后再写 → 一次写对
- 改完代码 → 跑测试 → 贴输出证据 → 你看到结果才算完
- 新窗口 → 读 HANDOFF.md + 模块文档 → 20 秒恢复上下文 → 直接干活

**这就是工作流的价值：用规则把 AI 框住，让它做正确的事。**

## 二、日常开发流程

### 完整流程图（你做什么 vs AI 做什么）

```
你：打开 Antigravity，开始新对话
      │
      │  ┌─ AI 自动做 ──────────────────────────┐
      │  │ 加载 6 个核心技能                      │
      │  │ 检查项目有没有 HANDOFF.md 和 docs/     │
      │  │ ─ 没有 → 提醒你要不要创建              │
      │  │ ─ 有 → 读取恢复上下文                  │
      │  └──────────────────────────────────────┘
      │
你：发送需求（比如"我想给聊天面板加搜索功能"）
      │
      │  ┌─ AI 自动做 ──────────────────────────┐
      │  │ 复述它的理解（1-2句话）                │
      │  │ 弹出选择框问你确认问题                 │
      │  │ （每个问题带 2-4 个建议选项）           │
      │  └──────────────────────────────────────┘
      │
你：选择选项 / 补充说明
      │  （可能来回 1-4 轮追问）
      │
      │  ┌─ AI 自动做 ──────────────────────────┐
      │  │ 生成 implementation_plan.md 计划文档   │
      │  │ ─ 里面写清楚：做什么、改哪些文件、      │
      │  │   怎么验证                              │
      │  │ ─ 如有不确定的，列出方案让你选          │
      │  └──────────────────────────────────────┘
      │
你：审阅计划文档
      │  ─ 觉得 OK → 回复"可以执行" / "approved"
      │  ─ 不满意 → 直接在文档上写评论批注
      │
      │  ┌─ AI 自动做 ──────────────────────────┐
      │  │ 创建 task.md 任务清单                  │
      │  │ 开始写代码                              │
      │  │ ─ 先写测试 → 再写实现                  │
      │  │ ─ 遇到 Bug → 根因分析，不瞎猜          │
      │  │ ─ 改完代码 → 跑测试、浏览器验证         │
      │  │ ─ 贴出测试结果截图/输出                 │
      │  └──────────────────────────────────────┘
      │
你：看到测试结果，确认是否满意
      │
      │  ┌─ AI 自动做 ──────────────────────────┐
      │  │ 更新 HANDOFF.md（记录做了什么）         │
      │  │ 更新 docs/ 模块文档（如果改了代码）     │
      │  │ 生成 walkthrough.md 变更总结            │
      │  └──────────────────────────────────────┘
      │
      ▼
     完成！
```

### 简化版：你只需要做 4 件事

| 步骤 | 你做什么 | AI 做什么 |
|------|---------|----------|
| **1. 提需求** | 用自然语言描述你想要什么 | 追问确认，帮你想清楚 |
| **2. 审计划** | 看计划文档，批注或通过 | 生成执行蓝图 |
| **3. 看结果** | 确认测试是否通过 | 写代码、跑测试、贴证据 |
| **4. 关窗口** | 感觉上下文太长时新开窗口 | 自动更新交接文档 |

**你不需要懂代码**，你只需要：
- 会描述"我想要什么效果"
- 会看懂"测试通过/失败"
- 会在文档上写评论

## 三、五种核心文档

### 文档家族全景图

```
你的项目目录/
│
├── HANDOFF.md              ← 🧠 项目的"外挂大脑"
│                              新窗口打开时 AI 第一个读的
│
├── docs/                   ← 📂 模块速查文档
│   ├── frontend-components.md   AI 改前端时读这个
│   ├── backend-api.md           AI 改后端时读这个
│   └── ...
│
└── （Antigravity 内部自动管理的文档，你看不看都行）
    ├── implementation_plan.md  ← 📋 执行计划（你审批用的）
    ├── task.md                 ← ✅ 任务清单（AI 跟踪进度用的）
    └── walkthrough.md          ← 📝 变更总结（做完后的记录）
```

### 每种文档详解

#### 🧠 HANDOFF.md — "外挂大脑"

**是什么**：你的项目的记忆档案。每次新开窗口，新的 AI "失忆"了，读这个文件就能恢复记忆。

**什么时候产生**：
- 新项目第一次用 AI 开发时，AI 会自动创建
- 之后每次完成重要工作时自动更新

**里面有什么**：
- 项目是什么、用什么技术
- 最近做了什么改动
- 下一步要做什么
- 绝对不能犯的错误（红线）

**你需要做什么**：通常不需要手动编辑。但如果你觉得某个信息很重要，可以让 AI 加进去。

---

#### 📂 docs/*.md — 模块速查文档

**是什么**：项目代码的"目录索引"。记录每个文件里有什么函数、在第几行、是干什么的。

**什么时候产生**：
- 新项目首次接入 AI 时，AI 全扫一遍项目自动生成
- 之后改代码时同步更新

**为什么重要（省钱原理）**：

```
没有模块文档时：
  AI 要改 ChatPanel.jsx 的一个函数
  → 必须读完整个文件（600 行）→ 花费大量 token
  
有模块文档时：
  AI 读 docs/frontend-components.md
  → 看到 "handleDelete() 在 L89"
  → 只读 L80-L120（40 行）→ 省了 90% 的 token
```

**你需要做什么**：不需要手动维护。AI 改完代码会自动更新。你只需要在第一次时让 AI 生成就行。

---

#### 📋 implementation_plan.md — 执行计划

**是什么**：AI 写代码之前给你看的"施工蓝图"。

**什么时候产生**：每次你提出新需求后，AI 追问完毕就会生成。

**你需要做什么**：
- **认真看**——这决定了 AI 接下来怎么改代码
- **满意** → 回复"可以执行"或"approved"
- **不满意** → 直接在文档上写评论，AI 会修改

---

#### ✅ task.md — 任务清单

**是什么**：AI 执行计划时的待办列表。标记哪些做完了、哪些正在做。

**你需要做什么**：通常不需要管。如果好奇进度可以看一眼。

---

#### 📝 walkthrough.md — 变更总结

**是什么**：AI 做完所有工作后的总结报告。

**你需要做什么**：可以看看了解这次做了什么改动，也可以不看。

## 五、新窗口怎么接着干

### 为什么要新开窗口？

AI 的"记忆"（上下文窗口）是有限的。对话太长，AI 会：
- 忘记前面说过的话
- 响应变慢
- 开始"胡说八道"

**经验法则**：做完一个大功能模块，或者感觉 AI 不太对劲了，就新开窗口。

### 什么时候该新开窗口？（上下文监测指南）

你可以用 `cxt` 命令查看当前上下文使用情况。它会显示类似这样的数据：

```
current total context: 154.7K
15.47% | 正常
```

这个百分比就是你的"上下文健康度"——代表 AI 的记忆已经被占用了多少。

#### 各模型新开窗口的建议阈值

| 模型 | 上下文总量 | 🟢 舒适区 | 🟡 注意区 | 🔴 必须新开 |
|------|----------|----------|----------|------------|
| **Gemini 2.5 Flash** | ~1M token | 0%-30% | 30%-50% | >50% |
| **Gemini 2.5 Pro** | ~1M token | 0%-30% | 30%-50% | >50% |
| **Claude Sonnet 4** | ~200K token | 0%-40% | 40%-60% | >60% |
| **Claude Opus 4** | ~200K token | 0%-40% | 40%-60% | >60% |
| **DeepSeek** | ~128K token | 0%-35% | 35%-55% | >55% |

#### 为什么不能用到 100%？

你可能会想："不是有 1M token 吗？用到 100% 不好吗？"

答案是：**AI 的注意力像一个 U 形曲线**。

```
注意力强度
  高 │  █████                           █████
     │  █████                           █████
     │   ████                          ████
     │    ███                         ███
     │     ██                        ██
  低 │      █████████████████████████
     └──────────────────────────────────────
         开头         中间              末尾
         (系统指令)    (历史对话)         (最新消息)
```

- AI **最关注**开头（你的规则和技能）和末尾（你最新说的话）
- **中间的历史对话**关注度最低——这就是"上下文太长 AI 开始胡说"的原理
- 对话越长，中间的"低注意力区域"越大，AI 越容易忽略重要信息

#### 以 Gemini 3.5 Flash 举例

Gemini 3.5 Flash 虽然有约 100 万 token 的上下文窗口，但：

- **0%-30%（~300K 以内）**：🟢 一切正常，AI 能很好地记住所有对话内容
- **30%-50%（300K-500K）**：🟡 开始出现轻微遗忘，可能忘记中间聊过的细节。**做完当前任务后就建议新开窗口**
- **50% 以上（500K+）**：🔴 明显退化，可能重复之前的错误、忘记约定。**立即保存 HANDOFF 然后新开窗口**

**为什么 Flash 建议更早换窗口（50% 而非 60%）？**
因为 Flash 是速度优先的模型，注意力分配不如 Pro/Opus 精准。同样的上下文长度，Flash 的中间遗忘更严重。

#### 实用建议

1. **养成习惯**：每完成一个完整功能，不管上下文百分比多少，都考虑新开窗口
2. **出现以下症状时立即新开**：
   - AI 开始重复你已经纠正过的错误
   - AI 忘记了之前约定好的方案
   - AI 的回复变得啰嗦且不着重点
   - AI 开始"创造性地"修改你没要求改的代码
3. **关窗口前一定要说**："更新 HANDOFF 和模块文档，我要关窗口了"

### 新窗口操作流程

**步骤 1**：新开一个对话窗口

**步骤 2**：对 AI 说：

> "读 HANDOFF.md，继续开发"

**步骤 3**：AI 会自动做以下事情（你不需要管）：
- 加载 6 个核心技能
- 读 HANDOFF.md 恢复项目上下文
- 准备好接收你的新需求

**步骤 4**：告诉 AI 接下来要做什么

就这么简单。HANDOFF.md 就是你的"存档"，新窗口就是"读档"。

## 六、模块文档系统

### 核心思想（一句话）

> **让 AI 查字典，而不是读课本。**

### 生命周期

```
项目诞生
  │
  ▼
首次全扫 → 生成 docs/（一次性，像拍一张全景照）
  │
  ▼
日常开发 → 改代码时顺手更新对应模块文档（像改照片上的标注）
  │
  ▼
定期校准 → 一周或一个版本全扫对比一次（确保字典没过时）
```

### 什么时候模块文档会被创建/更新

| 时机 | 谁触发 | 做什么 |
|------|--------|--------|
| 新项目首次接入 | AI 自动检查（阶段 0） | 全扫项目 → 生成全部模块文档 |
| 改了代码 | AI 自动（阶段 3/5） | 更新对应文件的函数行号和描述 |
| 新增了文件 | AI 自动 | 在对应模块文档中添加索引 |
| 删除了文件 | AI 自动 | 从模块文档中移除 |
| 一周一次 | 你手动提醒 | "扫一下项目，校准模块文档" |

### 你需要做什么？

**几乎什么都不用做**。唯一需要你做的是：
- 新项目时让 AI 初始化（说一句话就行）
- 偶尔提醒 AI "检查一下模块文档有没有过时"

## 八、常见问题

### Q: AI 没有追问就直接出计划了怎么办？
**A**: 直接说"你没有按流程来，先问我确认"。全局规则要求它必须追问，但有时候（尤其便宜模型）它会忘记。提醒一下就好。

### Q: 计划文档里废话太多怎么办？
**A**: 说"文档只写蓝图，不要解释"。规范已经写了不允许在计划里写碎碎念，提醒一下即可。

### Q: 模块文档的行号过时了怎么办？
**A**: 不影响使用——行号偏差几行 AI 还是能定位到。一周说一次"校准模块文档"就行。

### Q: 新窗口的 AI 好像没有加载技能？
**A**: 检查 GEMINI.md 文件是否完整。全局规则写在这里面，每次新对话都会自动读取。如果丢了，找这份指南里的记录恢复。

### Q: 用便宜模型效果不好怎么办？
**A**: 便宜模型可能会：不追问就直接干、计划写得粗糙、忘记跑测试。遇到这些情况直接提醒它。规则写得越明确，便宜模型越能遵守——这就是为什么我们把规则写得很详细。

### Q: 我的全局规则在哪？
**A**: `C:\Users\cixia\.gemini\GEMINI.md` — 这是 AI 的"行为准则"，每次对话自动加载。

### Q: 我的技能文件在哪？
**A**: `C:\Users\cixia\.gemini\antigravity-ide\skills\` — 所有技能都在这个目录下。

### Q: 怎么知道现在有多少个技能？
**A**: 问 AI "列出我所有的技能"即可。

## 写在最后

cixia，如果你正在读这段话，说明你可能过了一段时间回来看这份文档了。

这套工作流的核心设计理念只有三个字：**不怕慢**。

你在最初告诉我的一句话，我一直记着："我不怕慢，我需要稳。新手小白就很容易写偏，浪费 token 一直修不好。"

所以这套系统的每一个环节都是为了"稳"而设计的：
- **追问对齐** — 宁可多问一轮，也不要理解偏了写 300 行废代码
- **计划审批** — 宁可多等你看一眼，也不要做了半天发现方向全错
- **验证交付** — 宁可多跑一次测试，也不要空口说"修好了"结果没好
- **交接沉淀** — 宁可多写几行 HANDOFF，也不要下次新开窗口全忘了
- **模块文档** — 宁可多花一次全扫的 token，也不要每次都通读全部代码

这些"多花的时间"，换回来的是：**每一步都走对，不用返工**。

对于一个小白来说，这比什么都重要。

### 几个小建议

1. **信任流程，不要跳步**。哪怕 AI 看起来已经理解了，也让它走完追问。这是你的保险。
2. **大胆提需求**。你不需要用"技术语言"，说"我想让那个按钮好看点"就够了。AI 会追问细节的。
3. **勤开新窗口**。上下文过长是 AI 质量下降的最大敌人。做完一个功能就存档换窗口，像打游戏一样。
4. **红线是宝贝**。每次踩坑都让 AI 记到 HANDOFF 的红线里。踩过一次的坑，永远不要再踩第二次。
5. **这套系统是活的**。用着用着觉得哪里不好用，随时改。告诉 AI"我觉得追问太多了"或者"模板缺了这个"，它会帮你调整。
