# implementation_plan.md 编写规范

> 本文件定义了执行计划文档的格式、硬约束、验证流程和示例。
> 创建 implementation_plan.md 时必须遵守本规范。

---

## 一、硬约束（红线，违反即不合格）

### 🚫 文档纯净度红线
- **严禁**在文档中写对用户提问的回答和解释（放在正文对话里）
- **严禁**写执行过程中的碎碎念、思考过程、状态更新（放在 task.md 里）
- **严禁**写调试日志和错误排查记录（放在正文或 scratch 目录）
- **严禁**写只有问题没有建议的开放性问题（必须附带 2-4 个方案建议）

### 🚫 验证步骤红线
- **每份计划必须包含「验证计划」章节**，不允许省略
- 验证计划只允许包含以下一类或多类：
  1. **自动化测试**：仅限于终端命令行/测试脚本自动化测试
  2. **手动验证**：由用户自己在浏览器或客户端确认的步骤（如 UI 效果与交互）
- **禁止**在 UI 验证中使用 `browser_subagent` 工具执行任何自动浏览器测试，一律改由在“手动验证”部分写明详细的步骤供用户亲自点击检验以节省 Token。
- 如果改动涉及后端接口或数据库模型，**必须**包含自动化测试步骤。

### 🚫 结构完整性红线
- **必须**包含「目标描述」章节
- **必须**包含「变更清单」章节（列出具体文件和改动内容）
- **必须**包含「验证计划」章节
- 如有不确定的设计决策，**必须**包含「用户审阅要点」章节

## 二、文档结构模板

```markdown
# [目标描述]

简述要解决的问题或要实现的功能（2-3 句话）。

## 用户审阅要点

> [!WARNING]
> **请重点审阅以下决策：**

### 决策 1：[决策标题]
[描述需要用户决策的点]
- **方案 A**（推荐）：[具体描述] — [为什么推荐]
- **方案 B**：[具体描述] — [适合什么场景]
- **方案 C**：[具体描述] — [适合什么场景]

### 决策 2：[决策标题]
[同上格式]

---

## 变更清单

按组件/功能区域分组，依赖顺序排列（被依赖的先列）。

### [组件名称]

#### [MODIFY] [文件名](file:///绝对路径)
- 具体改动描述（改哪个函数/哪段逻辑）
- 改动原因

#### [NEW] [文件名](file:///绝对路径)
- 文件职责
- 关键接口说明

#### [DELETE] [文件名](file:///绝对路径)
- 删除原因

---

## 验证计划

### 自动化测试
- 命令：`[具体测试命令]`
- 预期：[预期输出/通过条件]

### 手动验证
- 步骤：
  1. 打开 [URL]
  2. 执行操作：[具体操作]
  3. 确认效果：[预期 UI 表现与交互反馈]
```

## 三、各章节编写指南

### 「目标描述」
- 2-3 句话说清楚"要解决什么问题"和"完成后用户能看到什么效果"
- 不要写技术细节，用用户能理解的语言
- 如果是 Bug 修复，描述"现在的问题是什么"和"修好后应该是什么样"

### 「用户审阅要点」
- 只列需要用户做决策的点，不要列纯技术细节
- 每个决策点必须给 2-4 个方案建议
- 用 `（推荐）` 标注你建议的方案，并说明推荐理由
- 用 `> [!WARNING]` 格式高亮，确保用户不会忽略

### 「变更清单」
- 按组件分组（前端/后端/配置等），不要按文件类型分
- 每个文件要说清楚"改什么"和"为什么改"
- 使用 `[MODIFY]` / `[NEW]` / `[DELETE]` 标签
- 文件名使用可点击链接格式 `[文件名](file:///绝对路径)`
- 修改已有文件时，尽量指明修改的函数/模块/行号范围

### 「验证计划」
**这是最容易被省略但最关键的章节。**

验证类型选择矩阵：

| 改动类型 | 自动化测试 | 手动验证 |
|---------|:---------:|:-------:|
| 后端接口 | ✅ 必须 | — |
| 前端 UI 布局/样式 | — | ✅ 必须 |
| 前端交互逻辑 | — | ✅ 必须 |
| 数据库模型 | ✅ 必须 | — |
| 全栈功能 | ✅ 必须 | ✅ 必须 |
| 纯配置修改 | ✅ 构建验证 | ⚪ 可选 |

**手动验证步骤规范**：
- 在计划中提供详细的、可操作的用户手动验证步骤。
- 步骤包括：访问哪个页面 URL → 逐个点击/输入哪些元素 → 预期看到什么样的视觉效果与控制台日志。
- 由用户人工在浏览器中进行最终体验性测试与冒烟测试。

## 四、开放性问题编写规范

### 优先用弹框，其次写文档

**第一选择**：在创建计划文档之前，用 `ask_question` 工具弹出选择框解决。
这样文档生成时就已经是无争议的纯净蓝图。

**第二选择**：如果多个问题之间有关联性（选了 A 影响 B 的方案），
可以写在文档的「用户审阅要点」中，但每个问题**必须附带建议方案**。

### 建议方案的格式要求

```markdown
### 决策 N：[简洁的问题标题]
[1-2 句话说明背景，为什么需要用户决策]

- **方案 A**（推荐）：[具体描述] — [推荐理由]
- **方案 B**：[具体描述] — [适合场景/取舍]
- **方案 C**：[具体描述] — [适合场景/取舍]
```

### 严禁的写法

```markdown
# ❌ 错误示范：空白问题
## 开放性问题
1. 搜索功能要支持哪些内容？
2. 按钮放在哪里？

# ❌ 错误示范：只有技术问题没有方案
## 开放性问题
1. 是否使用全文索引？需要评估性能影响。
```

## 五、追问对齐流程（在写计划之前执行）

收到任何新需求时，**先追问对齐，后写计划**：

```
收到需求
  │
  ▼
复述理解（1-2 句话，在正文中）
  │
  ▼
用 ask_question 弹出至少 1 个确认问题
（哪怕需求看起来很清晰，也要确认核心意图）
  │
  ▼
复杂任务：继续追问 2-4 个细节问题
  │ 每个问题附带 2-4 个建议选项
  │
  ▼
全部对齐后，生成 implementation_plan.md
  │
  ▼
等待用户审批 → 创建 task.md → 开始执行
```

**追问示例**：

用户说"给聊天面板加个搜索功能"

第 1 步（正文复述）：
> 我理解您想在聊天面板中增加搜索消息的功能。让我确认几个细节——

第 2 步（弹框追问）：
> **搜索范围应该包含哪些内容？**
> 1.（推荐）仅搜索用户发送的消息 — 最简单
> 2. 搜索所有消息含 AI 回复 — 更全面
> 3. 搜索消息 + 记忆内容 — 最强大但较复杂

第 3 步（根据回答继续追问）：
> **搜索结果的展示方式？**
> 1.（推荐）在聊天面板顶部加搜索栏，结果高亮显示 — 类似微信
> 2. 弹出独立搜索面板 — 不影响当前聊天
> 3. 侧边栏展示搜索结果列表 — 可以快速跳转

第 4 步：对齐完毕，生成干净的计划文档。
