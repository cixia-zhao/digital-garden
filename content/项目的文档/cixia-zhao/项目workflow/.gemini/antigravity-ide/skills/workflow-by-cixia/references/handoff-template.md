# HANDOFF.md 编写规范

> 本文件定义了项目交接文档的格式、硬约束和编写指南。
> 创建或更新 HANDOFF.md 时必须遵守本规范。

---

## 一、HANDOFF.md 的核心定位

HANDOFF.md 是**新窗口/新会话**打开时，AI 快速恢复项目上下文的"外挂大脑"。
它的目标是：让一个完全没有对话历史的 AI，读完这份文档后就能像老搭档一样继续工作。

### 硬约束

- **必须保持时效性**：每次会话完成重要工作后，都应更新"已完成的工作"部分
- **必须包含红线警告**：记录踩过的坑和禁止重犯的错误
- **必须包含核心文件地图**：新 AI 需要知道项目代码结构
- **严禁堆砌全部历史**：只保留"活跃上下文"（当前和前 1-2 次会话），更早的归入"历史沉淀"摘要
- **严禁写成技术文档**：这是交接备忘录，不是 API 文档
- **中文书写，杜绝不必要的英文括号翻译**

## 二、文档结构模板

```markdown

- **项目名称**: [名称]
- **工作区路径**: `[绝对路径]`

- **运行方式**: [如何启动项目]
- **构建与部署流程**: [构建命令和步骤]

## 🚀 2. 本次会话已完成的工作（最新会话）
```

## 三、各章节编写指南

### 「项目概览」
- 写给完全不了解项目的 AI 看，需要一目了然
- **必须包含运行方式**：新 AI 要能直接启动项目
- **必须包含构建流程**：尤其是前端构建 → 同步到后端的完整命令

### 「本次会话已完成的工作」
- 这是最重要的"活跃上下文"，需要详细
- 按功能模块分组，不要按时间顺序
- 每个模块列出涉及的文件（便于新 AI 快速定位）
- 写清楚"改了什么"和"为什么改"，而非仅仅"做了什么"

### 「历史工作沉淀」
- **压缩再压缩**：前几次会话的工作压缩为分类摘要
- 只保留对当前开发仍有影响的信息
- 具体实现细节可以省略——新 AI 可以直接看代码

### 「核心文件地图」
- 用树状结构，深度不超过 3 层
- 只列关键文件，不要列每一个文件
- 每个文件附带一句话说明用途

### 「待办事项」
- 按优先级排列
- 已知 Bug 排在功能开发前面
- 每项附带简短上下文说明

### 「红线警告」
- 这是经验沉淀，**极其重要**
- 记录每次踩坑后的教训
- 使用 `🚫 DO NOT` 格式，醒目且不易忽略
- 解释"为什么不能这样做"而非仅仅说"不要"

## 四、更新时机与策略

### 何时更新
- ✅ 完成一个重要功能模块后
- ✅ 修复一个重大 Bug 后（特别要更新红线章节）
- ✅ 发现新的"坑"或约定后
- ✅ 准备关闭当前会话、切换新窗口前

### 更新策略
- **「本次会话」→「历史沉淀」轮转**：新会话开始时，将上次的"本次会话"内容压缩合并到"历史沉淀"中，然后清空"本次会话"章节
- **模块文档联动**：更新 HANDOFF.md 时，检查 docs/ 下的模块文档是否也需要同步更新
- **文件地图按需更新**：只有新增/删除/重命名文件时才更新
- **红线只增不删**：教训是永久性的，除非明确确认已不再适用

### 体积控制
- 目标：整个 HANDOFF.md 控制在 **150-250 行**
- 超过 250 行时，压缩"历史沉淀"章节
- 核心文件地图只列关键文件（不超过 30 个）

## 五、常见错误

| 错误 | 正确做法 |
|------|---------|
| 把全部修改历史都堆在文档里 | 只保留最近 1-2 次会话详情，其余压缩为摘要 |
| 写成 API 文档或技术规范 | 这是交接备忘录，写给"新来的 AI 同事"看 |
| 忘记更新运行方式 | 项目启动方式变了必须同步更新 |
| 红线章节空空的 | 每次踩坑都要沉淀一条教训 |
| 文件地图过时 | 新增/删除文件后及时更新 |
| 中英混杂 | 保持纯中文，代码变量和专有名词除外 |
