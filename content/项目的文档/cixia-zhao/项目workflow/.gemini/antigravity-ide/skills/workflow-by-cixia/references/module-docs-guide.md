# 项目模块文档编写规范

> 本文件定义了项目级模块速查文档的创建、维护和使用规范。
> 目的：让新窗口的 AI 不需要通读全部代码，只读对应模块文档就能精准定位修改位置。

---

## 一、为什么需要模块文档

**问题**：项目变大后，每次新开窗口 AI 都要重新读大量代码文件，消耗大量 token，且容易"小小的胡说八道"。

**解决**：让 AI 首次全面读取项目后，生成模块速查文档。之后新窗口只需要：
- 读 `HANDOFF.md`（全局视角）
- 读对应的模块文档（局部细节）
- **直接跳到目标函数行号修改**，跳过"通读理解"环节

---

## 二、何时创建模块文档

- **项目首次接入 AI 开发时**：让 AI 全面扫描项目，一次性生成所有模块文档
- **新增重要模块时**：新建对应的模块文档
- **绝不需要每次会话都重新生成**

---

## 三、文档存放位置

```
项目根目录/
└── docs/
    ├── frontend-components.md    # 前端组件速查
    ├── backend-api.md            # 后端接口速查
    ├── backend-services.md       # 服务层逻辑速查
    └── ...按项目需要增加
```

**命名规则**：`[层级]-[模块名].md`，全部小写，用连字符分隔。

**划分粒度原则**：
- 中小项目（20 个文件以下）：按前后端分 2-3 个文档即可
- 中型项目（20-50 个文件）：按功能域分，每个域一个文档
- 大型项目（50+ 个文件）：每个独立模块/包一个文档

---

## 四、文档内容模板

每个模块文档包含以下部分：

```markdown
# [模块名称] 速查文档

> 最后更新：YYYY-MM-DD
> 覆盖文件：[文件列表简述]

## 模块职责
[2-3 句话说清楚这个模块做什么]

## 文件索引

### [文件名.ext]
- **路径**：`相对路径`
- **职责**：[一句话]
- **关键函数/组件**：
  - `functionName()` (L行号) — [功能描述]
  - `ComponentName` (L行号) — [功能描述]
  - `className.method()` (L行号) — [功能描述]
- **依赖**：[依赖的其他文件/接口]
- **被依赖**：[哪些文件依赖它]

### [下一个文件...]
[同上格式]

## 模块间关系
[可选。描述本模块与其他模块的调用关系，如"ChatPanel 调用 /api/chat/* 接口"]

## 已知问题与注意事项
[可选。记录已知 Bug、特殊约定、容易踩的坑]
```

## 五、关键函数索引的写法

**行号标注格式**：`functionName()` (L行号)

```markdown
# ✅ 好的写法 — 新 AI 能直接跳转
- `handleSend()` (L45) — 发送消息到后端，触发 AI 生成回复
- `handleDelete()` (L89) — 删除消息，用户消息触发级联删除
- `scrollToBottom()` (L156) — 平滑滚动到底部，手动接管 scrollTop

# ❌ 不好的写法 — 太模糊，没有定位价值
- handleSend — 发送消息
- 删除相关函数
- 滚动逻辑
```

**行号会过时怎么办？**
- 日常改代码时，如果改了关键函数的位置，顺手更新行号
- 不需要精确到个位数——标注到大致区域（如 L45 实际在 L48）也能帮 AI 快速定位
- 定期（一周或一个版本）做一次全量校准

## 六、更新策略

### 日常更新（改代码时同步）

改了代码 → 检查对应模块文档 → 更新以下内容：
- 新增/删除/重命名的函数
- 行号发生大幅变化的函数
- 新增的文件
- 变更的依赖关系

**只更新你改动的部分**，不需要重新生成整个文档。

### 定期全量校准（一周或一个版本）

让 AI 全面扫描项目文件，与模块文档做对比：
- 行号是否还准确
- 是否有新文件没加入文档
- 是否有删除的文件还留在文档里
- 函数描述是否还正确

提示词示例：
> "请扫描项目代码，与 docs/ 下的模块文档做对比，列出需要更新的地方"

## 七、新窗口使用流程

```
新窗口打开
  │
  ├─→ 读 HANDOFF.md（全局视角：项目是什么、技术栈、待办事项、红线）
  │
  ├─→ 用户提出需求："改一下聊天面板的 XXX"
  │
  ├─→ 读 docs/frontend-components.md（定位到 ChatPanel 部分）
  │       │
  │       └─→ 找到相关函数 handleXXX() 在 L89
  │
  ├─→ 只读 ChatPanel.jsx 的 L80-L120（而非通读 600 行）
  │
  └─→ 精准修改，节省大量 token
```

对比没有模块文档时：
```
新窗口打开
  │
  ├─→ 读 HANDOFF.md
  │
  ├─→ 用户提出需求："改一下聊天面板的 XXX"
  │
  ├─→ 通读 ChatPanel.jsx 全部 600 行（大量 token）
  │
  ├─→ 理解代码结构（大量思考 token）
  │
  └─→ 找到目标位置，开始修改
```

## 八、首次生成模块文档的提示词

当项目第一次需要创建模块文档时，使用以下提示词：

> "请扫描整个项目的代码文件，按照 docs/ 下的模块文档规范（参考 workflow-by-cixia 技能中的 module-docs-guide.md），为每个模块生成速查文档。重点标注关键函数的行号和职责。"

## 九、常见错误

| 错误 | 正确做法 |
|------|---------|
| 写成 API 文档（参数、返回值、示例） | 这是速查索引，不是 API 文档。重点是"什么函数在第几行做什么" |
| 试图记录每一个函数 | 只记录关键函数（入口函数、业务逻辑、容易改动的部分）|
| 从不更新行号 | 改代码时顺手更新，一周一次全量校准 |
| 整个项目放一个文档 | 按模块分文件，改前端时只读前端文档 |
| 模块文档写得比代码还长 | 每个文件的索引控制在 10 行以内 |

## 十、实战范例

> 以下片段摘自实际项目模块文档，供生成时参照。

### 前端组件写法示范

```markdown
### ChatPanel.jsx
- **路径**: `frontend/src/components/ChatPanel.jsx`
- **职责**: AI 聊天面板，管理消息收发、历史记录、记忆系统
- **关键函数**：
  - `ChatPanel({ onStateChange, apiUrl })` (L5) — 组件入口
  - `handleSend()` (L219) — 发送用户消息到 /api/chat，接收 AI 回复
  - `handleDeleteMessage()` (L135) — 删除单条消息，级联删关联 AI 回复
  - `handleClearHistory()` (L188) — 清空全部聊天历史（带确认弹窗）
  - `fetchChatHistory()` (L51) — 获取聊天历史记录
  - `fetchMemories()` (L73) — 获取 AI 记忆列表
- **依赖**: 后端 `/api/chat/*` 系列接口
- **被依赖**: `App.jsx`
```

**要点**：
- 组件入口必须写，标明 props
- 每个函数一行，格式固定：`函数名()` (L行号) — 一句话说明
- "依赖"和"被依赖"帮助 AI 理解改动的影响范围

### 后端接口写法示范

```markdown
### chat.py
- **路径**: `backend/app/api/chat.py`
- **职责**: AI 聊天接口
- **关键函数**：
  - `post_chat_message()` (L94) — `POST /api/chat` — 核心接口：接收消息，编译上下文，调用 AI，返回回复
  - `get_chat_history()` (L167) — `GET /api/chat/history` — 获取全部聊天历史
  - `delete_chat_message()` (L213) — `DELETE /api/chat/messages/{id}` — 删除消息
- **依赖**: `models.py`, `schemas.py`, OpenAI API
- **被依赖**: `ChatPanel.jsx`
```

**要点**：
- 后端函数除了行号外，**额外标注 HTTP 方法和路由路径**（如 `POST /api/chat`）
- 这让 AI 能直接理解前后端的对应关系

### 模块间关系图写法示范

```markdown
## 模块间关系

App.jsx（根组件 — 全局状态管理）
  │
  ├─→ ChatPanel     → /api/chat/*（独立管理消息和记忆）
  ├─→ FocusTimer    → /api/records/study（计时→创建记录）
  ├─→ Heatmap       ← data 从 App 传入（纯展示 + 事件）
  ├─→ Ledger        → /api/records/finance（收支记录）
  └─→ Settings      → /api/settings, /api/modes
```

**要点**：
- 箭头方向表示数据流向：`→` 表示主动调用，`←` 表示被动接收
- 一句话说明每个组件和后端的通信关系
- 不需要画完美的架构图，ASCII 文本即可

### 划分文档数量的参考

| 项目规模 | 文件数 | 建议文档数 | 划分方式 |
|---------|--------|-----------|---------|
| 小型 | <15 | 2 个 | 前端 + 后端 |
| 中型 | 15-40 | 3-4 个 | 前端组件 + 后端接口 + 后端核心 + [服务层] |
| 大型 | 40+ | 5+ 个 | 按功能域划分（用户模块、订单模块、支付模块…） |
